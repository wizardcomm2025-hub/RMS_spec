Developer guide

The 5-minute version

A short orientation for engineers picking up work against this repo. Read project-overview.md and conventions.md for the full picture; this is the fast pass.

Looking for a specific feature? Each features/<feature>/ directory has its own developer-guide.html with a plain-language overview and per-surface key points. Open it in a browser, then read this page after for the repo-wide rules.
Before there's a spec — intake/. Features in discovery don't live under features/ yet. The intake/ folder is where interview Q&A (from the spec-intake skill) and client-provided business rules accumulate before formal specs are written. Read its README if you're starting a new feature; ignore the folder once you're picking up a ticket against an existing one.

How the specs work

This folder is the single source of truth for what RMS does across the RMS API, the Tenant and Central databases and the Next.js admin dashboard. There is no code here — only specifications, API contracts, data models, UI/UX designs, test cases and architectural decisions. If you're implementing, you're working in RMS_API (reading these specs at ../App-Specs/) or RMS_NextJS (at ../../App-Specs/). Plans, task status and test results live in RMS_API/specs/<feature>/.

The mental model

Think of a feature as a vertical slice of behaviour, sliced again into use-cases. Each use-case is one user-observable behaviour — UI, API call, backend handler, data write — captured in a single file you can read end-to-end without jumping around.

features/<feature-name>/ ├── README.md ← what the feature is + index of use-cases ├── developer-guide.html ← plain-language overview + per-surface key points (open in a browser) ├── 01-<use-case>.md ← one user-observable behaviour, end-to-end ├── 02-<use-case>.md ├── data-model.md ← Tenant DB / Central DB tables and stored procedures ├── api-contract.md ← endpoints used by this feature ├── ui-ux.md ← admin-dashboard screen design (UI_UX_STANDARDS.md) └── test-cases/ ← tester (UI) + developer (direct API) test cases

The use-case file is the unit of work. It tells you what to build (Main flow), what state must be in place before you start (Prerequisites), what counts as done (Acceptance criteria), and what's specific to your surface (Platform notes → RMS API / Data — Tenant DB / Data — Central DB / Integrations / Admin dashboard).

Reading order when you pick up a ticket

  1. project-overview.md Product context and the glossary. The canonical definitions of shared terms.
  2. features/<feature>/developer-guide.html Plain-language overview and the section for your surface. Open in a browser.
  3. features/<feature>/README.md The formal feature index: scope boundaries, dependencies, open questions.
  4. The specific use-case file you're implementing One vertical slice, end-to-end. Read it in full before forming a plan.
  5. data-model.md, api-contract.md, and the relevant slice of api/openapi.yaml Schemas, endpoints, payload shapes. The contract you build against.

That's enough to implement one slice. You shouldn't need to read every other use-case in the feature.

Rules that bite if you ignore them

The spec describes what, not how

If it reads like pseudocode, the spec is wrong. If your code reads like the spec, you've under-implemented.

Behaviour is never duplicated across files

When one use-case depends on a rule defined in another, it links rather than restates. Duplication drifts.

Open questions stay in the document

Resolved questions get their answer and date appended in italics. Nothing gets deleted. The history matters.

Acceptance criteria are mandatory and observable

A tester must be able to derive pass/fail cases from them without asking. Behaviour observable from outside the system, not "the database row is updated".

If a Prerequisites bullet is unmet — pause or stub

Never blindly. Plan-mode reads that section as a readiness gate before forming an implementation plan.

When the spec is unclear

The order of operations is: check project-overview.md (the glossary in particular), check the feature README.md for cross-cutting open questions, then ask. Don't guess and don't infer from partial context. If something genuinely needs to change in the spec, that is a spec change here, approved by the user — not a unilateral decision in the implementation repo.
