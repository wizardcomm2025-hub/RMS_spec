How the spec repo works

Three stages, in order. Read this once and you'll know where things live, who does what, and which file to open when. Five minutes.

The two skills that do the work

Each stage has a skill that does most of the heavy lifting. You don't have to memorise the workflow — call the skill by name and Claude takes you through it. Skills live under .claude/skills/ and are auto-discovered.

spec-intake
Stage 1. Interviews you about a feature and writes each Q&A to intake/<topic>.md as you go. Open with "spec-intake on <feature>" or paste a Figma screenshot and ask for clarifying questions.
feature-spec-from-figma
Stage 2. Takes the intake file plus your Figma screenshots and drafts the formal spec under features/<name>/. Enforces clarify-before-draft so silent assumptions stay out.

There's also grill-me — same interview style as spec-intake but without writing to a file. Reach for it when you want to pressure-test a plan or an ADR rather than scope a feature.

Stage 1 of 3

1 Intake — before a spec exists

Gather everything you know about a feature-in-the-making, before it's structured enough to be a spec.

Who: UX & product, with Claude
Where: intake/<topic>.md
Status: collecting

Two ways content lands in the same file:

  • Interview Run the spec-intake skill. Tell Claude what feature you're scoping (paste a Figma screenshot if you have one). Claude asks questions one at a time, you answer, and each Q&A is appended to intake/<topic>.md as the conversation proceeds — nothing is lost mid-session.
  • Drop-in No skill needed. Got a fact from a client call or stakeholder? Open intake/<topic>.md directly and add a bullet under What we've been told. This replaces "developer notes" inside Figma.

The file goes quiet, not away. When the formal spec is written, the intake stays as the audit trail. Flip Status: collecting → Status: spec-written and link the new spec at the bottom of the intake file.

Stage 2 of 3

2 Write the spec — when intake is rich enough

Turn the raw Q&A and facts into a structured spec the team can build from.

Who: Feature lead (UX/PM with eng input)
Where: features/<name>/
Trigger: You can describe what the feature does, not just what someone wants
  1. Run the feature-spec-from-figma skill. Point it at the intake file and your Figma screenshots. The skill asks any remaining blocking questions, then drafts the use-case files, README.md, and developer-guide.html under features/<name>/ — following the section template in conventions.md and copying the styling from features/template/.
  2. Review the draft. Fill in data-model.md, api-contract.md, ui-ux.md and test-cases/ with engineering input — they need backend judgment about Tenant DB tables, stored procedures, the CompanyId boundary and endpoint messages.
  3. Get approval from the product owner and one engineer per affected repo (RMS_API, RMS_NextJS). Then write plan.md and tasks.md in RMS_API/specs/<name>/.

After approval, flip the intake file's status and link the new spec files at the bottom of it.

Stage 3 of 3

3 Live feature — engineers implementing

Engineers in the implementation repos picking up a ticket against a feature that's already specced.

Who: Engineers in RMS_API, RMS_NextJS
Where they look first: features/<name>/developer-guide.html

Reading order for one ticket:

  1. developer-guide.html (one-time orientation to the repo itself)
  2. project-overview.md — the glossary in particular
  3. features/<feature>/developer-guide.html — the per-surface "what matters where you sit" section
  4. features/<feature>/README.md — scope, dependencies, open questions
  5. The specific use-case file (NN-<use-case>.md)
  6. data-model.md, api-contract.md, and the relevant slice of api/openapi.yaml

That's enough to ship one vertical slice. You shouldn't need to read every other use-case in the feature.

When in doubt — ask

Don't infer. If a spec is missing, ambiguous, or contradicts another spec, stop and ask. Open questions belong in the document (the intake file or the use-case file), not in your head. The history of why a decision was made is as valuable as the decision itself — that's why nothing here is ever deleted, only superseded.
