Plain-language onboarding for engineers picking up work on this feature. The structured index is in README.md; the use-case specs are the NN-<use-case>.md files in this folder. This guide points you at what to read.

What this feature does

A Location is a place a company operates — an outlet, a warehouse or a central kitchen. Stock, users, requisitions, wastage, PO receive and POS all hang off it. This screen lets a company admin list, add and edit locations, assign employees, pick one Default Location, and switch a location off instead of deleting it. In the database it is still called Warehouse.

v1 scope

Fix the defects found on 2026-10-28 (POS flag wiped, duplicate edit reported as success, unauthenticated get-by-id, bins wiped on save, owner overwritten, no name limit) and replace delete with an Active / Inactive switch. The page is also the reference design for every list page. See README.md for the formal scope, decisions and open questions.

How it works end-to-end

The admin dashboard calls POST /Setting/* endpoints with the user's token and the company's Origin. The tenant middleware picks the Tenant DB from the host; the controller takes CompanyId and UserId from the token and calls stored procedures on dbo.Warehouse. Inactive means IsActive = 0, IsDeleted = 0: every other screen already filters on IsActive = 1, so a switched-off location disappears there and stays visible here.

Read 02 and 03 (one save contract), then 04 for the new ChangeWareHouseStatus. Messages are in api-contract.md. Never trust CompanyId from the body.
