# 05 — Email a purchase order to the vendor

**Actor:** a company user with `create_purchase_order`.
**Goal:** send a submitted purchase order to the vendor (distributor) as a PDF by email.

## Main flow
1. On a **Submitted** PO, the user clicks **Email to vendor**. The action is in the list row (and phone card) actions and in the footer of the View dialog.
2. The **Email purchase order** dialog opens, prefilled by the server:
   - **To**: the vendor's active contact emails (`DistributorContact.Email`).
   - **CC**: the PO creator's email.
   - **Subject**: `Purchase order {PO number} from {restaurant name}`.
   - **Message**: `Dear {vendor name},` + blank line + `Please find attached our purchase order {PO number}. Kindly confirm receipt.` + blank line + `Regards,` + new line + `{restaurant name}`.
   - **Attachment** (read only): `PO-{PO number with "/" as "-"}.pdf`.
   - **Last emailed** (only if it was sent before): `Last emailed {date time} to {emails}`.
3. The user can edit To, CC, subject and message, then clicks **Send**.
4. The server checks the PO again, builds the PDF, and sends it from the **platform mailbox**. The From name is the restaurant's name and Reply-To is the sender's email. It records the send.
5. On success the dialog closes with the snackbar "Purchase order emailed to vendor".

## Alternate flows
- **A1 Vendor has no email**: To is empty and the dialog shows "This vendor has no email. Add one in Vendor, or type an address." Send stays disabled until To has an address.
- **A2 Re-send**: allowed any number of times; each send is recorded and "Last emailed" updates.
- **A3 Draft or Cancelled PO**: the action is not shown. The API refuses: "Only submitted purchase orders can be emailed."
- **A4 Mail not set up**: no active platform `EmailTemplate` secret → "Email isn't set up yet. Contact support." (dialog stays open).
- **A5 Send fails** (SMTP error): "Couldn't send the email. Please try again." The failure is recorded with its error; dialog stays open with what was typed.

## Rules
| # | Rule |
|---|---|
| R1 | Only POs of the caller's company with status **Submitted** can be emailed. |
| R2 | To: 1–10 addresses; CC: 0–10; every address valid (`name@domain.tld`, max 100 chars); duplicates removed, case-insensitive. |
| R3 | Subject required, max 200 characters. Message optional, max 2000 characters, sent as plain text (HTML-encoded; line breaks kept). |
| R4 | The PDF is built on the server from the saved PO, never from what the screen sends. It shows: the restaurant name, address and GSTIN; the vendor; the PO number, date and status; the lines (item, description, qty, unit, rate, amount); the total; and the footer "Generated by RMS". |
| R5 | Sent from the platform mailbox (Central `PlatformNotificationSecret`, `ServiceName = 'EmailTemplate'`). From name = restaurant name; Reply-To = the sender's user email, else the restaurant's `AdminEmail`. |
| R6 | Every attempt is written to `PurchaseOrderEmailLog`, success or failure. |
| R7 | The PO itself does not change (status, `UpdatedAt` untouched). |

## Acceptance criteria
1. A Submitted PO shows **Email to vendor** in the list, the phone card and the View dialog. Draft and Cancelled POs don't show it.
2. The dialog opens prefilled exactly as in step 2. With no vendor email, A1's text shows and Send is disabled.
3. Send with valid input delivers an email with the PDF attached. The success snackbar shows, and "Last emailed" is updated when the dialog opens again.
4. Invalid input shows the field errors in `ui-ux.md` and nothing is sent.
5. Every API refusal shows its message in the dialog. Nothing is sent and the PO is unchanged.
6. The dialog works from 360 px (full screen) to 1920 px. While sending, the Send button shows a spinner and the dialog is locked, so a double click can't send twice.
